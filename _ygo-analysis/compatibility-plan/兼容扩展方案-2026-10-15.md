# 扩展兼容方案与官方资源核查（2026-10-15）

## 用户确认的目标

保留全部原物品、原卡牌和原卡包，扩展到连接时代前；决斗相关逻辑统一由 MDPro3 规则内核和 Lua 脚本接管，避免逐卡编写 Java 效果。优先采用原模组依赖附属的实现方式，保留原注册名及原物品存档身份。

## 工作量判断

这是较复杂的规则引擎替换与兼容扩展工程。批量卡图转换和数据导入可以自动化；主要成本在原物品与内核卡号映射、询问应答 UI、网络同步及旧附属冲突。整体应按数周以上的迭代工程理解，精确排期需要 P0 引擎验证通过后给出。

## 已核实的兼容接口

- 原 CardItem 绑定固定 CardDefinition，公开 definitionOf(ItemStack)、isCard(ItemStack) 等入口。
- 原 CardDefinition 使用字符串 id，没有灵摆刻度字段；不能直接完整承载 MDPro3 的卡片模型。
- 原 Expansion 保存 id、code、officialName、cardIds，可以保留已有卡包及开包行为，新增卡包建立独立数据记录。
- interaction-fix 对决斗逻辑、网络和客户端均有大量 Mixin；不能假定新规则引擎与这些规则补丁自然兼容。

## 推荐实现

1. 保留原注册物品及卡包 ID，不删除旧物品。
2. 建立原卡 ID / 附属卡 ID -> ocgcore 卡号的映射，保留原卡面和稀有度。
3. 新卡可采用一个或少量通用 CardItem + NBT 卡号；必须适配原卡盒、识别入口、图鉴及开包流程。
4. 所有进入新决斗的旧卡与新卡均由同一 ocgcore 结算；阻断旧 Java 效果的重复执行。
5. 分离可保留的物品/交易/外观功能与需要停用或改写的旧规则 Mixin；逐项验证 ygostar 与 interaction-fix。
6. 无法可靠映射、缺脚本或超出卡池范围的旧卡需要形成审计清单；保留物品身份不等于强行允许进入截止日卡池。

## 资源风格统一

本地 art_vs_closeup.png 证实 Art 示例为方形插画、Closeup 为透明主体立绘。Art 不应直接拉伸成 176x257 完整卡面。
已有卡面保持原模组风格；新增卡面需要统一卡框、中文字体/排版、属性与星级、数值、灵摆框及刻度。先以代表性卡片比较清晰度，再确定打包分辨率。立绘等比缩放并保留透明边缘，按需加载及释放纹理。
官方包装图统一适配原模组物品模型、尺寸与透明边缘；缺图必须记录，不能声称全部已收集。
