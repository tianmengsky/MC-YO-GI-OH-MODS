## 1. 最终目标与不可破坏的约束

用户已确认：**保留全部原物品、原卡牌、原卡包及其存档身份，扩展连接时代前的卡池与卡包；决斗相关代码由 MDPro3 规则内核和卡片脚本接管，避免逐张重写 Java 效果；新增资源与原模组风格统一。**

| 项目 | 执行约定 |
|---|---|
| 时间边界 | 沿用已确定的连接前边界：发行日期 ≤2017-03-24；不是 2017 年全年，也不是简单地删掉连接怪兽 |
| 决斗规则 | 大师规则 3；无额外怪兽区，支持融合、仪式、同调、超量及灵摆 |
| 原物品 | 不更换原注册名；原物品、卡盒、卡包、决斗盘及其他已有物品继续存在 |
| 原卡包 | 保留原包 ID、原收录配置和旧物品身份；历史考据数据另存，不能悄悄覆盖旧包行为 |
| 新卡效果 | 优先直接使用配套 ocgcore 与 Lua 脚本；缺失或不兼容形成报告，不能冒充无效果卡 |
| 模组形态 | 优先新增兼容附属，依赖原模组；需要调整现有修复附属时保留其物品注册和非决斗功能 |
| 原生调用 | 正式运行在服务端 JVM 进程内；不采用常驻 sidecar。隔离子进程只用于开发期原生探测 |
| 私服 | 服务端权威，支持本地单人和私人服务器；客户端负责输入和表现 |
| 原资源 | 已有外观优先保留；新增卡面、包装、悬浮立绘按统一规范处理 |
| 数据范围 | 产品完整盘点与游戏实际投放分开；赠卡、赛事奖励、预组不能全当成随机补充包 |
| 交叉验证语言 | 按用户最新指示，仅英文、日文、中文；英日官方产品收录为主，MDPro3 中文卡库补中文名/描述和规则字段。其他语言不作为本轮交付要求 |

“保留物品”与“允许在截止日卡池中决斗”是两件事。如果原附属已有截止日之后的卡，物品仍保留，严格卡池规则下给出明确的组卡提示，不删除或变成其他卡。历史范围外卡片数量必须先审计。

本计划默认使用 MDPro3 当前配套效果文本及脚本，再限制卡池和大师规则；**这不等于完整复刻 2017 年勘误、裁定与禁限卡表**。若要求历史效果复刻，应新增独立工作包，不能把现代脚本直接称为 2017 原版效果。

## 2. 已知事实、旧诊断修正与待验证项

### 2.1 可以作为依据的事实

- 原 `CardItem` 持有固定 `CardDefinition`，卡片为独立注册物品，卡定义使用字符串 ID。
- 原 `CardDefinition` 没有灵摆刻度字段，不能直接完整承载新内核的数据模型。
- 原 `Expansions.Expansion` 包含 `id/code/officialName/cardIds`；原卡包内容可单独冻结。
- 原 `BoosterItem` 有独立开包、池缓存、稀有度与发卡流程，需要保留或适配。
- `interaction-fix 0.103.2` 有 102 个通用 Mixin、20 个客户端 Mixin，不能假定与新内核自然兼容。
- MDPro3 提供中文卡库、原生规则内核、配套 Lua 脚本、Art 插画及 Closeup 透明立绘。
- MDPro3 `pack.db` 以卡号为主键，每卡只有一行，不能表达完整的多包重印关系。
- KONAMI 官方 `cid` 是数据库身份，不能直接当作 ocgcore 卡号。

### 2.2 必须修正的旧结论

1. 不再采用“必须抛弃本体”的路线。先验证附属接管能力，保留原模组的物品与资产；决斗协议和 UI 需要较大改写不代表旧物品必须丢弃。
2. 不再以“2 参数调用不崩”认定 `new_card` 是结构体 API。读取本机程序集后，两套托管封装均声明它为 7 参数。
3. `create_duel_v2` 的托管声明是 `uint32[]`；数组长度和实际调用点仍需验证，不能套用现代 API 的种子布局。
4. `Percy.CardData.Setcode` 是内嵌 `int16[16]`，另一套 YGOSharp 数据结构使用 `int64`。不得混用现代 `setcodes` 指针布局。
5. Art 示例是方形插画，不是完整竖版卡面。旧文档直接估算“Art 缩成完整卡面”的容量只能视作未定稿样本。
6. 旧文档中的 8201 张卡、立绘数量和容量是基于既有数据的初步测量，正式构建必须由冻结源数据重新生成报告。

### 2.3 尚不能预先宣布通过

- 原生放卡、启动对局、真实回调布局、大师规则参数和连续回合推进。
- 英日官方目录是否遗漏早期、撤下或特定地区产品；本轮不再扩采其他语言。
- 全卡官方 CID 到内核卡号的可靠映射。
- 旧附属非决斗功能能否在接管规则后完整保留。
- PNG 调色板、字体、缩放和透明边缘在当前客户端的实际效果。
- Linux 私服所需原生库；当前现成二进制为 Windows x64，不能在 Linux 上直接使用。

证据位置：`F:\Minecarft\游戏王mod工作区\mdpro3-p0\ffi-extract\核查结论-2026-10-15.md` 与同目录 `decoded-signatures.txt/decoded-layouts.txt`。

### 2.4 本轮补充的静态资源审计

`mdpro-input-audit.json` 已重新核对冻结 MDPro3 数据的日期过滤结果：8201 张候选卡（5458 怪兽、1495 魔法、1248 陷阱），全部有同卡号 Art 文件。207 张灵摆卡均有同卡号脚本和立绘。7558 张候选卡有同卡号专属 Lua，其余 643 张恰好为非灵摆通常怪兽，不应直接列作缺脚本。

同卡号 Closeup 共 6352 项，其中怪兽立绘 5444 项，魔法 538 项、陷阱 370 项；**不能把 6352 说成 6352 张怪兽都有立绘**。14 张怪兽未找到同卡号立绘，完整名单在审计 JSON。开发时先检查可用异画/补图，再使用明确回退显示。文件存在性不是图像正确性或脚本运行成功的证明；最终卡池仍需和官方源数据对比。

### B03 官方卡片与 MDPro3 卡号映射

映射优先级：可核对的印刷八位卡号或可信外部 ID 关联 > 多字段一致并有印刷编号证据 > 名称等候选匹配。仅名称相等不能自动升为“已确认”。

外部卡库的 `id` 可能是异画/资源 ID，而非规范印刷密码。例如本次盘点发现黑魔术师资源 ID `46986420` 在 MD 中可通过异画 alias 归到 `46986414`。源 API ID、资源 ID、规范引擎 passcode 分列保存；只有本地名称、文本及规则字段等证据确认是同一规则卡的异画时才归一。不能把全部 `datas.alias` 都折叠成同一卡，否则可能误合并“规则上视为同名”但实际效果不同的卡。

分别保存 `official_cid`、`engine_passcode`、异画/别名关系、映射方法、证据来源、置信状态。令牌、无卡号卡、特别版本、同名不同 ID 等允许保留未映射状态。

比赛奖品卡、收藏展示卡或注明“不能用于正式决斗”的产品收录仍进入历史源数据库，另存 `official_use_restriction/playability` 及原页证据。它们不应因日期符合而自动进入普通卡组或普通抽卡配置。对带游戏限制的特殊卡与普通可用再版，应分别保留印刷/官方身份再核对规则卡号。

使用中文卡库补中文名和描述，不改写官方原名；保存原文和本地展示名两列。卡号按整数保存并在展示时补足八位，不能将前导零当成不同卡。

## 6. 工作包 C：原生内核 P0——先证明能正确决斗

### C01 锁定真实 API、回调和规则参数

1. 读取 MDPro3 实际调用点，确定 Percy/YGOSharp 哪条封装驱动本机 DLL。
2. 提取所有调用约定、参数宽度、结构体布局、种子数组长度、options 构造和消息格式。
3. 确认配套公共 Lua 的读取顺序、路径、编码及脚本缓冲区寿命。
4. 输出一份与冻结 DLL 哈希绑定的 API 合同，禁止仅根据上游现代文档推测。

已提取声明仅供入口定位：

```text
new_card(handle, uint32 code, uint8 owner, uint8 player,
         uint8 location, uint8 sequence, uint8 position)
create_duel_v2(uint32[] seeds)
start_duel(handle, uint32 options)  // Percy 声明
card_reader(uint32 code, CardData* out) -> uint32
script_reader(name, int32* length) -> pointer
```

这些声明仍需结合实际调用与本 DLL 验证；不是把本计划抄成桥接代码就算成功。

### C02 最小放卡验证

1. 在隔离子进程加载冻结 DLL，注册日志/卡数据/脚本读取回调，并持有强引用。
2. 用确认的数据结构填一张普通怪兽数据，记录所有字段与写入字节数。
3. 创建决斗、设置玩家、放一张卡，调用 `query_field_count` 验证牌堆数量。
4. 验证回调确实触发并返回预期数据；再扩展到双方各 40 张牌。
5. 多次创建/销毁，确认回调、句柄和脚本缓冲区生命周期正确。

验收：放卡数量匹配、无越界/崩溃、卡数据可读回；仅函数不崩溃不算通过。

### C03 启动与三回合消息流

1. 用最简合法牌组启动，记录 `process/get_message` 及每次响应。
2. 正确解析抽卡、新回合、阶段和可行动请求，使用最小响应器完成至少 3 个回合。
3. 验证胜负、认输、正常结束和销毁；保存随机种子、牌组、响应及原始消息日志。
4. 确认大师规则 3 的真实设置与查询结果；以灵摆区域和额外牌组召唤行为验证，不只检查界面没有额外怪兽区。
5. 分别验证融合、仪式、同调、超量、灵摆与一次连锁；缺脚本与公共库错误必须可追踪。

### C04 脚本覆盖与卡池兼容

逐卡核对脚本依赖、别名和公共库。通常怪兽不必各自有专属 Lua，不能用“每个卡号必须有 c<ID>.lua”作为错误判据；需要区分无须专属脚本、借用别名脚本、专属脚本缺失和公共依赖缺失。

验收：P0 结果包括 API 合同、MR3 配置、可复现三回合日志、召唤/连锁样例、缺脚本报告。P0 未过时先解决签名、布局与配套版本；若考虑更换内核，记录兼容差异并单独验证，不能无声切换。

## 7. 工作包 D：旧卡身份与新卡物品兼容

### D01 建立统一卡牌领域模型

新模型独立于原 `CardDefinition`，至少包含 passcode、alias、setcodes、type 位、等级/阶级、属性、种族、攻守、左右灵摆刻度、额外牌组类型、名称、描述及来源版本。

保留未知攻击力/守备力等原始值；不得把负值随意归零。数据库 `setcode` 打包值到内核固定数组的转换按 C01 合同实现，不把整数误当指针。

### D02 映射所有旧卡与衍生物

1. 将 A02 的旧字符串 ID 与 MD 卡号建立带证据映射。
2. 原版卡、附属卡、金卡/异画、衍生物分别审计；外观变体不必产生新的规则身份。
3. 保存反向映射，使开新包抽到已有旧卡时优先产出原物品，避免同卡无理由出现两套身份。
4. 别名、异画与“同名卡最多三张”的检查按引擎/卡库规则统一处理。
5. 无法映射的原卡保留物品并提示；严格决斗构建前拒绝，不能代换成看似相近的卡。

产物：`legacy-card-id-map.csv/unmapped-legacy-cards.csv/card-identity-spec.md`。

### D03 新物品与旧入口适配

新增卡优先采用通用 `CardItem + NBT passcode/rarity/schema_version`，具体注册方式由兼容原型确定。原物品不批量替换成新通用物品。

读写适配应保留不属于本附属的 NBT、原有金卡/光效/自定义名称等标记；不能为增加卡号而重建整份物品 NBT 并丢掉未知字段。数据版本用于兼容迁移，异常字段给出报告，不静默改卡。

适配 `isCard/definitionOf` 等入口、旧卡盒槽位规则、卡组保存、图鉴、创意展示、JEI、开包发卡、商店和交易。旧定义只作为兼容视图；规则逻辑不能依赖它缺失的灵摆字段。

验收样例：旧卡与新卡混放同一卡盒；存取、重启、交易、丢弃再拾取后身份及稀有度一致；无物品丢失/复制；旧存档不出现 missing registry。

具体身份示例：原物品 `yugioh:blue_eyes_white_dragon` 继续作为原物品保存，解析后得到内核卡号 `89631139`，不要求把旧物品先转换成新卡。作为灵摆数据样例，MDPro3 的 `76794549` 对应“宙读之魔术士 / Astrograph Sorcerer”，本地首发记录为 SD31-JP001、2016-12-23；它的左右刻度应从新模型读取，不用旧定义缺失的字段猜测。示例卡已存在于哪些原附属仍以 A02 审计为准，不能仅凭名字将它重复注册。

## 8. 工作包 E：卡包、预组与构筑

### E01 分离历史真值与游戏投放配置

源数据记录历史收录，投放配置决定游戏里如何获得。新增产品配置至少包含产品键、显示名、地区标识、物品模型、可抽卡集合、数量、稀有度策略及获取方式。

缺少官方抽率时使用明确的游戏配置；不能把旧模组的抽率称为 KONAMI 官方概率。重印卡可被多个包抽到，但基础卡牌身份保持一致。

### E02 原包原样保留，新产品按类型接入

1. 冻结原包 ID 与内容，对比新版本开包输出范围。
2. 新随机包从完整 `product_cards` 生成，不用首发归属表拼包。
3. 预组按经过核实的数量发卡，不随机抽；数量未知产品暂不作为“完整预组”投放。
   复合商品先建立“外包装产品 → 内装包/促销卡/预组”关系，再计算开盒发放；实物组成未知时只展示已核实的收录资料，不按赠卡列表模拟完整开盒。
4. 赛事包、赠卡和套装保留独立产品身份，根据玩法配置获取途径。
5. 增加卡包详情与收录查看；同名跨地区产品显示地区，防止玩家混淆。
6. 开包在服务端完成，扣包与发卡保持一致；满背包、断线和重复请求不得吞包或复制卡。

### E03 卡组构筑与合法性

实现中文/英文/原卡名搜索，卡型/属性/种族/等级/额外牌组/灵摆/卡包/日期筛选。服务端核对主卡组、额外、备牌数量，同名限制、卡池范围及所选禁限表。

禁限表必须带地区、日期和规则配置 ID；初版沿用原可选格式或明确的自定义规则，不暗中指定一张未经确认的“2017 禁卡表”。卡池、规则和禁限表在开局前形成双方一致的会话配置。

## 9. 工作包 F：Java 桥接、消息协议与服务端会话

### F01 开发工程与桥接选择

建立 Forge 1.20.1 / Java 17 独立工程，固定依赖版本，运行基线 JAR 作为本地开发依赖而非打包进附属。配置构建、运行客户端及独立服务器。

正式桥接保持 JVM 内嵌。优先先验证最小 JNI 薄桥；若 JNA 更适配且不改变进程内目标，需记录依赖、回调寿命、结构布局与性能比较后确定，不将两条路线混写成已实现。

按 DLL 哈希/协议版本绑定桥接；检查位数和原生依赖，错误时给出可操作日志。客户端连接独立服务器时不要求加载服务端内核；单人集成服务器需要可用内核。

### F02 内存与线程合同

- 原生句柄唯一所有者，所有同一对局操作串行执行。
- 未证明全局回调和 DLL 多对局线程安全前，使用专用串行执行器；不得从渲染线程或任意网络回调直接调用。
- 不将耗时 `process` 无限阻塞 Minecraft tick；设置批次与步数预算，记录卡死状态并中止会话。
- 回调不得向原生边界抛出 Java 异常；脚本/卡库读取失效要记录并明确终止。
- 保持回调和缓冲区存活，明确每个指针谁分配、何时释放；资源释放具有幂等性。
- 普通 Java 超时不能安全抢占任意卡死的原生函数，进程内崩溃可能带走服务器；上线前必须以隔离测试及配套版本降低此风险。

### F03 消息协议解析

以本 DLL 消息协议为准，为每个消息建立字段、长度、可见性、是否请求响应及响应格式表。不能套用现代核心的字段宽度。

按组实现：启动/抽卡/阶段；卡片移动与区域；召唤与战斗；连锁和确认；选择卡片/目标/区域/位置；可取消选择与反复勾选；费用/计数器/排序/总和选择；宣言卡名/种族/属性/数字；胜负和错误。

未知消息必须记录原始数据并停止当前对局，不能当作已处理继续推进。测试要覆盖边界、缺字节、非法响应、同一请求重复响应和真实内核消息样本。

### F04 会话与联网

每场对局保存会话 ID、参与者、随机种子、规则配置、协议版本、请求 ID、序列号、生命周期与清理状态。服务端验证玩家身份、轮到谁操作、请求仍有效、索引/数量合法。

分别生成双方与观察者视图，遮蔽手牌、里侧卡、未知牌序等秘密信息；不能先把完整状态发给客户端再由 UI 隐藏。状态序列支持丢包后的重同步；日志也区分公开版与管理员原始版。
