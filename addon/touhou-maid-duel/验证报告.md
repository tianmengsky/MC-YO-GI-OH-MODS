## 2026-10-18 0.1.5：对手机（AI）动作世界朝向重定向

问题定位（实机为 `geckolib:winefox`，`YsmModelId` 为空）：

- 旧实现把 YGO 姿势的局部四元数转成欧拉角后逐轴取反，手臂链还额外反转 Z。`Quaternionf.rotationZYX` 构造的四元数不能靠“把欧拉分量取反”得到镜像旋转：对 `(10,20,30)` 取反 x/y 后与原旋转差 1.3°，三个分量全取反最多差 163°，手臂因此反向或扭到错误一侧。
- 原生傀儡的腿挂在 `all` 下，酒狐的腿挂在 `AllBody > DownBody` 下。只复制局部旋转会让女仆腿多吃一层 `Body` 旋转，抽卡/攻击帧误差可达 58°。
- 旧实现还把映射骨骼的位置和缩放清零；原生姿势的位置通道没有应用。0.1.5 明确只对齐朝向，保留女仆自身骨骼比例与服装。

修复内容：

- `MaidDuelAnimation` 改为四元数世界朝向重定向：原生局部旋转 → 原生世界旋转 → 身体/头/腿用 `(x,y,-z)`（X 前后、Y 转身同向，Z 侧摆镜像）→ 用女仆父骨骼当前世界朝向反解局部旋转；**双臂直接复制原生局部旋转**。腿的父级差异因此被自动补偿。
- 人形链上的辅助骨骼（`MRoot/MAllbody/MUpBody/MUpperBody/UpperBody/Arm/AllHead/MHead/DownBody`）先回到绑定旋转；头发、尾巴、耳朵、裙摆、定位骨骼等未映射分支不动，继续播放 TLM 原动画。
- 四元数转欧拉改用 `Matrix4f.rotation(q).getEulerAnglesZYX(...)`。JOML 1.10.5 的 `Quaternionf.getEulerAnglesZYX` 不是 `rotationZYX` 的逆（实测 `(10,20,30)` 返回 `(8.68,20,30)`），不能直接使用。
- 加入一次性运行时报文 `MAID_RETARGET_READY maxError=... deg`：在真实客户端第一次绘制女仆立绘时校验“反解后的世界朝向 vs 原生目标”。缺少骨骼时输出一次 `MAID_RETARGET_SKIP`，该模型回退到自身动画。

离线核对：

- 用 `puppet.bin` 的 9 段动作与 `winefox.json` 的完整父子链逐帧计算，比较头、躯干、上臂、前臂、腿的世界方向。旧算法平均误差 25–63°、最大 180°；世界朝向解法在 Python 模型上为 0.0°（四元数浮点误差 < 0.1°）。
- TLM 1.5.3 的 `RotationValue.processValue` 对 Bedrock 动画 X/Y 取负、Z 保留，`GeoBuilder` 对模型旋转做同样处理；但那是 **TLM 自己的 Bedrock 模型** 到 Gecko 的换算。YGO 原生傀儡与女仆的镜像关系不同：X 俯仰、Y 转身与女仆同向，Z 侧摆镜像；身体/头/腿最终用 `(x,y,-z)`。这个结论不是推出来的，是用 `run-debug` 的原生/女仆同帧对照和实机朝向逐项验证的（见下文）。

### 0.1.5 首轮实机复现与第二处修复（四元数别名）

首轮 0.1.5（`829A...`）实机进入女仆决斗后，红色对手立绘板上没有模型，只有播放动作时头发/尾巴短暂闪入，然后落回下方；用户确认不是“模型消失”，而是模型被移出立绘带。

为此新增本地自调试场景，而不是继续让用户反复进游戏：

- `run-debug/`：开发专用实例，`mods/` 硬链接真实模组，使用 PCL 同款生产 classpath 直接启动；不写原游戏目录。
- `generated/maid-debug/MaidDebugScene.java`：仅调试构建注入，`-Dmaid.debug=true` 时打开调试画面，用真实 `MaidPortraitRenderer` 和真实 `EntityMaid`/`winefox` 渲染；输出 `debug-view-*.png` 与 `debug-duel.png`。调试类已从发行源码移除，不会进入 0.1.5 发行 JAR。
- 复现结果：`debug-view-4.png`（完全不重定向的女仆）完整、直立、脚在 y=229；`debug-view-0.png`（生产路径）为空；`debug-view-5.png`（重定向）只剩底部头饰碎片。说明问题在 `MaidDuelAnimation`，不是相机/裁剪。

根因是 `nativeWorld` 的**原地四元数乘法别名**：

```java
world[bone] = parent < 0 ? local
        : nativeWorld(parent, world).mul(local).normalize();
```

`nativeWorld(parent, world)` 返回的是缓存数组中的**父骨骼世界四元数对象**，`mul(local)` 直接把它改写为“父世界 × 本地”。于是 `natives[0]` 先被 `Body` 改写、再被后续骨骼继续污染，最终变成 `root×Body×Body2×…`；`wanted` 用的是被污染的目标，`MAID_RETARGET_READY maxError=0.0` 只是“反解对了错误目标”。日志实测：

```text
MAID_DEBUG_NATIVE allLocal=(0.0130,-0.3423,0.0279,0.9391)
                  allWorld=(0.8212,-0.1181,0.4085,0.3805)
MAID_DEBUG_BONE Root x=-125.48 y=49.53 z=10.38
```

修复为：

```java
world[bone] = parent < 0 ? local
        : new Quaternionf(nativeWorld(parent, world)).mul(local).normalize();
```

修复后同一调试场景的日志：

```text
MAID_DEBUG_NATIVE allLocal=(0.0130,-0.3423,0.0279,0.9391)
                  allWorld=(0.0130,-0.3423,0.0279,0.9391)
MAID_DEBUG_BONE Root x=-0.40 y=40.06 z=3.26
MAID_DEBUG_BONE AllBody x=0.00 y=7.50 z=0.00
MAID_DEBUG_BONE RightArm x=-10.26 y=4.69 z=71.02
```

`debug-view-0.png` 中原生立绘路径重新出现直立的酒狐（头/躯干在 0..138 带内）；`debug-duel.png` 中红色对手板上出现女仆，和左下玩家立绘同框，模型不再移出画面。上面的 `MAID_DEBUG_BONE` 世界目标日志来自中间版本（仍是 `Rz` 镜像）；最终动作口径的结论见下一节。

### 0.1.5 第三处修复：身体朝向、双臂原生局部、副手盘

第二轮实机反馈：立绘虽然回来了，但动作不像原生人机，决斗盘卡在脖子处、没有端到身前；随后用户指出原生人机本身也是**左手（副手）**拿盘。

- `run-debug` 调试场景增加“同一 `中二拍卡` 帧的原生对手 vs 女仆”对照。Z 轴镜像 `(-x,-y,z)` 不对：原生 Root 从 `Y=-40°` 转到 `Y=+58°`，女仆被镜像成 `Y=-58°`，整只转向背面；右臂原生 `X=+145°` 向前，女仆变成向后，盘落到脖子/身后。
- 对 8 种四元数符号组合逐个渲染，身体/头/腿先定到 **`(x,-y,-z)`**；它解决了“盘被甩到身后”，但实测身体朝向变成**屏幕右侧**（人物左侧），和用户要的“人物右侧/屏幕左侧”相反。
- 第三轮按用户实机截图把身体/头/腿的 Y 改回同向，即 **`(x,y,-z)`**：X 前后、Y 转身同向，Z 侧摆镜像。这样身体/脸转向**屏幕左侧/棋盘**，和原生对手一致。
- **双臂仍不能继续用世界镜像**：原生左臂在 `中二拍卡` 是 `(-26.7,-66.1,3.8)` + 前臂 `(101.3,3.7,8.3)` 的弯肘，和右臂 `(145.2,26.4,54.2)` 不是镜像关系。用世界镜像反解左臂会把副手盘甩到左后方。最终**双臂直接使用原生局部旋转**（同侧手臂复制局部），身体/头/腿用世界 `(x,y,-z)`。
- 曾短暂把立绘盘改到主手验证过前臂朝向，但用户确认原生也是副手后已**撤回**：立绘实体保持副手（左手）盘，主手清空。

最终待机/动作的副手盘都在胸前，身体朝屏幕左侧/棋盘。`MAID_RETARGET_READY` 的世界朝向自检现在只覆盖身体/头/腿；双臂是原生局部旋转，不参与该世界误差统计。
